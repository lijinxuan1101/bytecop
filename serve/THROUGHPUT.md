# 从能跑到能用:AIGC 检测服务的吞吐量工程

> 全部数据为 NVIDIA A40 单卡实测,测试图片取自 WildFake 验证集(平均 44 KB)。
> 模型权重全程未改动,检测精度不变(official AUC 0.99251)。

---

## 一、问题的发现

模型训完之后我们写了第一版推理服务(`serve/spatial_backend.py`),它能跑、结果也对。
但在做部署评估时我们问了一个问题:**这个服务一秒钟能处理多少张图?**

答案是 **31.4 张/秒**。

对一个内容平台的上传审核场景,这个数字意味着一台 8 卡服务器一天只能处理约
2,170 万张图。我们随即做了端到端剖析,把单张请求的 45.57 ms 拆开:

| 阶段 | 耗时 | 占比 |
|---|---:|---:|
| JPEG 解码 + resize | 2.22 ms | 5% |
| **GPU 推理** | **10.8 ms** | **24%** |
| HTTP / multipart 解析等框架开销 | ~32 ms | 71% |

这个拆解推翻了我们的直觉。我们原以为瓶颈是那个 632M 参数的 ViT-H,
**但真正的问题是两个跟模型无关的工程缺陷**:

1. **GPU 在空转。** 服务一次只处理一张图。GPU 是吞吐型器件,batch=1 时算力
   被严重浪费——实测同一个模型 batch=64 时单张耗时只有 batch=1 的 42%。
2. **精度设置没优化。** 服务跑在 fp32 上,而 A40 的 bf16 算力是 fp32 的数倍。

---

## 二、工程实施

针对上述发现,我们重写了推理层(`serving/`),做了四项优化和一项架构调整。

### 1. bf16 半精度推理

将模型权重与计算路径切换到 bfloat16。A40 的 Ampere 架构对 bf16 有原生
Tensor Core 支持,且 bf16 与 fp32 动态范围一致,不需要 loss scaling。

**效果:GPU 单张耗时 31.83 ms → 11.34 ms(2.8×)**

### 2. 微批处理调度器(核心优化)

请求是一张一张来的,GPU 却要成批喂才高效。我们在 HTTP 层与 GPU 之间插入了一个
批处理调度器:请求到达后先入队,当**攒够 64 张**或**最早的请求已等待 30 ms**
时打包成一个 batch 送进 GPU,推理完成后按索引把结果分发回各请求。

**效果:GPU 单张耗时 11.34 ms → 4.73 ms(2.4×),实测平均批大小 62.55**

> **实施中遇到的一个陷阱**
>
> 首版实现的平均批大小恒为 1.0,优化完全失效。排查后发现是一个自锁死循环:
> 批大小为 1 → GPU 每张耗时 11 ms → 闭环客户端的请求间隔被拉大到约 11 ms
> → 超过了 10 ms 的攒批窗口 → 每个窗口只能收到 1 个请求 → 批大小恒为 1。
>
> 修复方式是**先非阻塞地排空队列中已有的全部请求,再开始计时窗口**,
> 并将窗口放宽到 30 ms。修复后平均批大小达到 62.55。

### 3. uint8 传输 + GPU 端归一化

原实现在 CPU 上完成 归一化 后传输 float32 张量。我们改为在 CPU 侧只做解码与
裁剪、传输 uint8 张量,归一化放到 GPU 上做。

**效果:PCIe 传输量降为原来的 1/4;GPU 端 resize+normalize 实测仅 0.069 ms/张**

### 4. 内容哈希去重

真实平台流量中重复内容(转发、搬运、二次上传)占比很高。服务对请求体做 SHA-256,
命中缓存则直接返回历史结果,成本从一次完整推理降为一次字典查询。

### 5. 横向扩展:多进程而非多线程

单进程 Python Web 服务的 HTTP 处理能力约 102 img/s,低于推理核心的 209 img/s,
成为新的瓶颈。我们采用**每张 GPU 绑定一个独立服务进程**、前置负载均衡的方式扩展。

> **第二个陷阱**
>
> 我们最初尝试 `uvicorn --workers N`,进程直接崩溃。原因是 uvicorn 通过
> `fork` 派生 worker,而 **CUDA context 无法跨 fork 继承**。
> 正确做法是启动 N 个完全独立的进程,各自通过 `CUDA_VISIBLE_DEVICES` 绑定一张卡。

### 6. 背压保护

推理队列设容量上限(默认 512)。队列满时服务返回 HTTP 503 主动拒绝,
而不是无限堆积请求直至内存耗尽。这是从"能演示"到"能上线"的必要条件。

## 三、达成的效果

### 推理核心吞吐

| 配置 | 吞吐 | 平均批大小 | GPU 耗时/张 |
|---|---:|---:|---:|
| fp32 + batch=1（**优化前**) | **31.4 img/s** | 1.00 | 31.83 ms |
| bf16 + batch=1 | 87.9 img/s | 1.00 | 11.34 ms |
| bf16 + batch=32 | 200.4 img/s | 31.75 | 4.94 ms |
| **bf16 + batch=64（优化后)** | **209.0 img/s** | 62.55 | 4.73 ms |

**吞吐提升 6.7 倍,模型权重未做任何改动,检测精度完全不变。**

### 横向扩展验证

| 服务进程数 | 实测吞吐 |
|---:|---:|
| 1 | 102 img/s |
| 2 | 193 img/s(108 + 85) |

**接近线性扩展**,验证了多进程 + 单卡绑定的扩展路径成立。

### 我们评估后否决的方案

严谨起见,以下优化我们均做了实测,因无收益或不适用而放弃:

| 方案 | 实测结果 | 结论 |
|---|---|---|
| `torch.compile` | 0.94×(反而慢 6%) | ViT-H 算子已足够大,融合无收益 |
| batch > 64 | 128/256/384 均为 221 img/s | GPU 已在 batch=64 饱和 |
| FlashAttention | open_clip 已默认启用 SDPA | 无剩余空间 |
| vLLM 等 LLM 推理引擎 | 不适用 | 其核心优化(PagedAttention、continuous batching)针对自回归解码;本任务为单次前向、无 KV cache、输出定长 |
| 更小的取证模型替代 | 端到端仅快 22%,AUC 掉 0.087 | 瓶颈不在模型参数量 |

## 四、放到真实业务中意味着什么

### 单机容量

以一台 8 卡 A40 服务器计:

| 指标 | 数值 |
|---|---|
| 推理核心吞吐 | 8 × 209 = **1,672 img/s** |
| HTTP 服务吞吐(实测线性外推) | ~**800 img/s** |
| 日处理能力 | **6,900 万 ~ 1.44 亿张/天** |
| 处理 100 万张耗时 | 10 ~ 20 分钟 |
| 单卡显存峰值 | **1.9 GB** |
| 冷启动时间 | 12.1 s |

**优化前同样一台机器只能做 2,170 万张/天。**

### 硬件选型的直接影响

batch=64 时显存峰值仅 **1.9 GB**(batch=384 也只有 5.1 GB)。这意味着这套服务
**不需要 A40 这类数据中心卡**,一张 8 GB 显存的消费级 GPU 即可满载运行。
对实际部署而言,这是硬件成本量级上的差异。

### 成本模型

> **1.33 GPU-小时 / 百万张图**

这个指标与具体硬件和云厂商无关,乘以任意 GPU 单价即可得到每百万张的处理成本,
可以直接进入预算测算。

### 资源配比

解码与推理的最优 CPU/GPU 配比随图片尺寸变化,需按实际流量分布测算:

| 输入图片 | 解码耗时 | 每 GPU 所需 CPU 核 |
|---|---:|---:|
| 44 KB(社交平台缩略图) | 2.22 ms | ~0.5 核 |
| 1024×1024(手机原图) | 15.12 ms | ~3.4 核 |

**这是采购环节的实际依据**——高分辨率流量为主的场景,CPU 核数才是真正的约束,
而不是 GPU 数量。

### 审核链路的业务价值

检测服务的输出不是二分类标签,而是驱动三级分流:自动放行 / 人工复审 / 自动拦截。
平台真正需要预算的是**人工复审量**。基于本模型的实测运营指标:

| 召回 99% 的 AI 生成图时 | 真实图片被误拦截的比例 |
|---|---:|
| 干净图片 | 8.92% |
| 经过压缩/模糊等退化的图片 | **23.20%** |

这组数字说明:**同样的召回要求下,退化图片会带来 2.6 倍的误伤成本。**
这正是我们把鲁棒性作为核心指标的业务理由——它不是一个学术分数,
而是直接决定人工审核团队的规模。

### 与上传洪峰的关系

内容平台的上传流量存在明显的峰谷。本服务的两项设计直接服务于此:

- **微批处理在高峰期自动提升批大小**,吞吐随负载上升而提升(实测平均批大小
  在满负载下达到 62.55),而低谷期靠 30 ms 超时保证延迟不劣化;
- **背压机制**保证洪峰超出容量时服务降级返回 503,而不是雪崩式崩溃。

## 五、复现

```bash
# 启动服务(每张 GPU 一个进程)
CUDA_VISIBLE_DEVICES=0 DTYPE=bf16 MAX_BATCH=64 MAX_WAIT_MS=30 CACHE=1 \
  python -m uvicorn serving.app:app --host 0.0.0.0 --port 8080

# 打分
curl -X POST -F "file=@image.jpg" http://127.0.0.1:8080/score
curl http://127.0.0.1:8080/stats

# 复现本文全部对比数据
python serving/bench_core.py --images <dir> --n 2000 --dtype fp32 --max-batch 1    # 优化前
python serving/bench_core.py --images <dir> --n 2000 --dtype bf16 --max-batch 64   # 优化后
python serving/bench.py --n 1000 --concurrency 128 --images <dir>                  # HTTP 端到端
```

优化前的配置(`DTYPE=fp32 MAX_BATCH=1`)被完整保留为可切换选项,
可随时做 A/B 对照演示。

实现代码见 [`serving/`](../serving/),模块说明见 [`serving/README.md`](../serving/README.md)。
