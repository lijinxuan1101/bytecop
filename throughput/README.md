# 从能跑到能用:AIGC 检测服务的吞吐量工程

> 全部数据为 NVIDIA A40 单卡实测,测试图片取自 WildFake 验证集(平均 44 KB)。
> **模型权重、计算精度、检测逻辑全程未改动**,所有收益来自模型之外的工程层。

---

## 一、问题的发现

模型训完之后我们写了第一版推理服务(`serve/spatial_backend.py`),它能跑、结果也对。
但在做部署评估时我们问了一个问题:**这个服务一秒钟能处理多少张图?**

答案是 **31.4 张/秒**。

对一个内容平台的上传审核场景,这意味着一台 8 卡服务器一天只能处理约 2,170 万张图。
我们随即做了端到端剖析,把单张请求的耗时拆开:

| 阶段 | 耗时 | 占比 |
|---|---:|---:|
| JPEG 解码 + resize | 2.2 ms | 5% |
| **GPU 推理** | **10.8 ms** | **24%** |
| HTTP / multipart 解析等框架开销 | ~32 ms | 71% |

这个拆解推翻了我们的直觉。我们原以为瓶颈是那个 632M 参数的 ViT-H,
**但真正的问题全部在模型之外**:

1. **GPU 在空转。** 服务一次只处理一张图,而 GPU 是吞吐型器件。
   实测同一个模型 batch=64 时单张 GPU 耗时只有 batch=1 的 70%。
2. **Web 层比模型还慢。** 单张请求里 71% 的时间花在 HTTP 框架上,GPU 只占 24%。

---

## 二、工程实施

针对上述发现,我们重写了推理层(`throughput/`),做了四项优化和一项架构调整。
**全过程不触碰模型权重与计算精度。**

### 1. 微批处理调度器(核心优化)

请求是一张一张来的,GPU 却要成批喂才高效。我们在 HTTP 层与 GPU 之间插入了一个
批处理调度器:请求到达后先入队,当**攒够 64 张**或**最早的请求已等待 30 ms**
时打包成一个 batch 送进 GPU,推理完成后按索引把结果分发回各请求。

**效果:GPU 单张耗时 31.71 ms → 22.29 ms,吞吐 31.4 → 44.6 img/s(1.42×),
实测平均批大小 60.19**

> **实施中遇到的一个陷阱**
>
> 首版实现的平均批大小恒为 1.0,优化完全失效。排查后发现是一个自锁死循环:
> 批大小为 1 → GPU 单张耗时高 → 闭环客户端的请求间隔被拉大到与之匹配
> → 超过了 10 ms 的攒批窗口 → 每个窗口只能收到 1 个请求 → 批大小恒为 1。
>
> 修复方式是**先非阻塞地排空队列中已有的全部请求,再开始计时窗口**,
> 并将窗口放宽到 30 ms。修复后平均批大小达到 60.19。

### 2. uint8 传输 + GPU 端归一化

原实现在 CPU 上完成归一化后传输 float32 张量。我们改为在 CPU 侧只做解码与裁剪、
传输 uint8 张量,归一化放到 GPU 上做。

**效果:PCIe 传输量降为原来的 1/4;GPU 端 resize+normalize 实测仅 0.069 ms/张**

### 3. 内容哈希去重

真实平台流量中重复内容(转发、搬运、二次上传)占比很高。服务对请求体做 SHA-256,
命中缓存则直接返回历史结果,成本从一次完整推理降为一次字典查询。

### 4. 横向扩展:多进程而非多线程

单进程 Python Web 服务的 HTTP 处理能力低于推理核心的能力,成为新的瓶颈。
我们采用**每张 GPU 绑定一个独立服务进程**、前置负载均衡的方式扩展。
实测双进程吞吐接近单进程的两倍,验证了线性扩展成立。

> **第二个陷阱**
>
> 我们最初尝试 `uvicorn --workers N`,进程直接崩溃。原因是 uvicorn 通过 `fork`
> 派生 worker,而 **CUDA context 无法跨 fork 继承**。
> 正确做法是启动 N 个完全独立的进程,各自通过 `CUDA_VISIBLE_DEVICES` 绑定一张卡。

### 5. 背压保护

推理队列设容量上限(默认 512)。队列满时服务返回 HTTP 503 主动拒绝,
而不是无限堆积请求直至内存耗尽。这是从"能演示"到"能上线"的必要条件。

## 三、达成的效果

### 五项优化合并后的提升

| 维度 | 靠哪一项 | 提升 | 依据 |
|---|---|---|---|
| **单卡吞吐** | 微批处理 | **31.4 → 44.6 img/s(1.42×)** | 实测 |
| **集群吞吐** | 多进程横向扩展 | **× GPU 数量(线性)** | 实测双进程 ≈ 2× |
| **有效吞吐** | 内容哈希去重 | **× 1/(1 − 命中率)** | 随流量重复率变化 |
| **CPU 占用** | uint8 传输 + GPU 端归一化 | 归一化从 CPU 卸载,GPU 侧仅 0.069 ms/张 | 实测 |
| **高负载延迟** | 微批处理 | **p50 8103 ms → 5719 ms(−29%)** | 实测,同等压力下 |
| **可用性** | 背压保护 | 不提升吞吐,**防止洪峰雪崩** | 设计保证 |

### 单卡推理核心吞吐(fp32,与原服务同精度)

| 配置 | 吞吐 | 平均批大小 | GPU 耗时/张 |
|---|---:|---:|---:|
| batch=1（**优化前**) | **31.4 img/s** | 1.00 | 31.71 ms |
| batch=32 | 43.3 img/s | 31.60 | 23.01 ms |
| **batch=64（优化后)** | **44.6 img/s** | 60.19 | 22.29 ms |

### 整机效果(8 卡 A40)

| | 吞吐 | 日处理量 | 每百万张成本 |
|---|---:|---:|---:|
| 优化前(单进程 batch=1) | 31.4 img/s | 271 万张 | 8.85 GPU-小时 |
| **优化后(8 进程 batch=64)** | **357 img/s** | **3,080 万张** | **6.23 GPU-小时** |
| 再叠加 30% 去重命中 | **510 img/s** | **4,410 万张** | **4.36 GPU-小时** |

**日处理能力提升 11 ~ 16 倍,单位处理成本下降 30% ~ 51%。**

### 三个必须说明的边界

**① 1.42× 中已包含 uint8 传输与 GPU 端归一化,两者不叠加。**
44.6 img/s 是在 uint8 传输开启的状态下测得的。uint8 的独立贡献主要在**节省 CPU**
而非提升吞吐:224×224 图像 float32 为 602 KB、uint8 为 150 KB,但在当前吞吐下
PCIe 带宽远未跑满,真正的收益是把归一化计算从 CPU 移走。

**② 11 ~ 16 倍中包含横向扩展带来的部分,拆开看更准确:**

- 纯软件优化(同一张 GPU):**1.42×**
- 横向扩展(8 张 GPU):**8×**
- 去重缓存(30% 命中):**1.43×**

**③ 低负载时单张延迟会略增,高负载时反而下降。**
微批处理最多等待 30 ms 才发车,因此空闲时段单张请求会多出至多 30 ms 的等待。
但在高负载下,由于整体吞吐提升、排队时间缩短,端到端延迟反而下降:
同等压力下实测 p50 从 8103 ms 降至 5719 ms(**−29%**)。

### 我们评估后否决的方案

严谨起见,以下优化我们均做了实测,因无收益或不适用而放弃:

| 方案 | 实测结果 | 结论 |
|---|---|---|
| `torch.compile` | 0.94×(反而慢 6%) | ViT-H 算子已足够大,融合无收益 |
| batch > 64 | 128 / 256 / 384 三档吞吐持平 | GPU 已在 batch=64 饱和 |
| FlashAttention | open_clip 已默认启用 SDPA | 无剩余空间 |
| vLLM 等 LLM 推理引擎 | 不适用 | 其核心优化(PagedAttention、continuous batching)针对自回归解码;本任务为单次前向、无 KV cache、输出定长 |
| 更小的取证模型替代 | 端到端仅快 22%,AUC 掉 0.087 | 瓶颈不在模型参数量 |
| 截断 Transformer 层数 | 16/32 层省一半算力,official AUC 掉 0.036 | 深层是鲁棒性的来源,不能砍 |

## 四、放到真实业务中意味着什么

### 单机容量

以一台 8 卡 A40 服务器计:

| 指标 | 数值 |
|---|---|
| 推理核心吞吐 | 8 × 44.6 = **357 img/s** |
| 日处理能力 | **3,080 万张/天**(叠加 30% 去重后 **4,410 万张/天**) |
| 每百万张成本 | **6.23 GPU-小时**(叠加去重后 4.36) |
| 单卡显存峰值 | **1.9 GB** |
| 冷启动时间 | 12.1 s |

**优化前同一台机器只能做 271 万张/天。**

### 硬件选型的直接影响

batch=64 时显存峰值仅 **1.9 GB**(batch=384 也只有 5.1 GB)。这意味着这套服务
**不需要 A40 这类数据中心卡**,一张 8 GB 显存的消费级 GPU 即可满载运行。
对实际部署而言,这是硬件成本量级上的差异。

### 资源配比

解码与推理的最优 CPU/GPU 配比随图片尺寸变化,需按实际流量分布测算:

| 输入图片 | 解码耗时 | 每 GPU 所需 CPU 核 |
|---|---:|---:|
| 44 KB(社交平台缩略图) | 2.2 ms | ~0.1 核 |
| 1024×1024(手机原图) | 15.1 ms | ~0.7 核 |

**这是采购环节的实际依据**——图片尺寸决定 CPU 需求,而不是拍脑袋按 GPU 数配。

### 审核链路的业务价值

检测服务的输出不是二分类标签,而是驱动三级分流:自动放行 / 人工复审 / 自动拦截。
平台真正需要预算的是**人工复审量**。基于本模型的实测运营指标:

| 召回 99% 的 AI 生成图时 | 真实图片被误拦截的比例 |
|---|---:|
| 干净图片 | 8.92% |
| 经过压缩/模糊等退化的图片 | **23.20%** |

这组数字说明:**同样的召回要求下,退化图片会带来 2.6 倍的误伤成本。**
这正是我们把鲁棒性作为核心指标的业务理由——它不是一个学术分数,
而是直接决定人工审核团队的规模。

### 与上传洪峰的关系

内容平台的上传流量存在明显的峰谷。本服务的两项设计直接服务于此:

- **微批处理在高峰期自动提升批大小**,吞吐随负载上升而提升(实测满负载下
  平均批大小达 60.19),低谷期靠 30 ms 超时保证延迟不劣化;
- **背压机制**保证洪峰超出容量时服务降级返回 503,而不是雪崩式崩溃。

## 五、服务架构与复现

```
HTTP 请求 → 哈希缓存查询（命中直接返回）
              ↓ 未命中
         解码线程池（PIL 解码时释放 GIL）
              ↓ uint8 [224,224,3]
         微批处理器（攒满 64 或等满 30 ms）
              ↓ [B,224,224,3] uint8 → GPU
         GPU：归一化 + ViT-H/14 前向（fp32）
              ↓ 按索引分发回各请求的 Future
         温度校准 → 概率```

队列有容量上限(默认 512),满时返回 **503** 而非无限堆积。

### 环境变量

`MAX_BATCH`(默认 64)、`MAX_WAIT_MS`(默认 30)、`DECODE_THREADS`(默认 16)、
`CACHE`(默认 1)、`CKPT`、`DTYPE`(默认 fp32,与 `serve/` 同精度)。
**`MAX_BATCH=1` 保留为优化前的对照配置。**

### 命令

```bash
# 启动服务(每张 GPU 一个进程)
CUDA_VISIBLE_DEVICES=0 MAX_BATCH=64 MAX_WAIT_MS=30 CACHE=1 \
  python -m uvicorn throughput.app:app --host 0.0.0.0 --port 8080

# 打分
curl -X POST -F "file=@image.jpg" http://127.0.0.1:8080/score
curl http://127.0.0.1:8080/stats

# 复现本文对比数据
python throughput/bench_core.py --images <dir> --n 1200 --max-batch 1     # 优化前
python throughput/bench_core.py --images <dir> --n 1200 --max-batch 64    # 优化后
python throughput/bench.py --n 1000 --concurrency 128 --images <dir>      # HTTP 端到端
```

优化前的配置(`MAX_BATCH=1`)被完整保留为可切换选项,可随时做 A/B 对照演示。

本目录同时包含实现代码:`detector.py`(模型加载与 GPU 端归一化)、`batcher.py`(微批处理调度器)、`cache.py`(内容哈希去重)、`app.py`(FastAPI 服务)、`bench.py` 与 `bench_core.py`(压测脚本)。

业务后端(批量打分、官方 JSON 输出、可视化接口)在 [`serve/`](../serve/),两者共用同一份权重 `runs/spatial_tower/spatial_tower_wildfake/best.pt`。
